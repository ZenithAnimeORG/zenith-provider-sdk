# Provider worker IPC protocol

`ProviderWorkerProtocol` defines the versioned wire contract between Zenith.App and an isolated provider worker. It is independent of the SDK artifact version, which remains `0.1.0`; the current wire `protocolVersion` is `1`.

Each UTF-8 JSON frame carries a request ID, optional `inReplyTo` correlation ID, protocol version, and a sealed message body. A worker first receives `Initialize` and answers with `Ready`, then handles typed `Invoke` calls and replies with `Complete`. While an invocation is running, the worker may issue correlated `BrokerRequest` messages; the host answers with `BrokerComplete`. Cancellation targets a request ID, and disposal is an explicit request/acknowledgement pair. Unsupported versions, malformed IDs, invalid checksums, oversized frames, and oversized blob metadata must be rejected.

The operation unions cover the SDK's catalog, media, torrent, poster, skip-timing, subtitle, tracker, import, stream-extractor, provider-test, provider-status, and provider-action contracts. Stream-extractor capability probes return a typed boolean result, and status probes return the serializable `ProviderStatusInfo` model. The broker union covers HTTP, provider settings, effective mirrors, and stream resolution. Payloads use concrete serializable SDK models; the wire contract contains no provider object, arbitrary path, reflection name, or opaque `Any` value.

Binary content is transferred as ordered `BlobChunk` frames addressed by a `ProviderWorkerBlob` token containing only a transfer ID, byte length, and SHA-256 checksum. Each chunk is at most 12 KiB, a blob is at most 32 MiB, and each encoded JSON frame is at most 96 KiB. Chunks must correlate to the request that declared the token. Transports must enforce complete ordered transfer, exact declared length, checksum validation, bounded concurrent transfers, and cleanup on cancellation. The token is not a filesystem path or an authorization capability.

`ProviderWorkerAdapter` exposes a worker session through the SDK's provider contracts. The host must construct it with the manifest parsed from the installed archive; it rejects a worker handshake whose manifest differs. It refuses undeclared capabilities, preserves worker failures as typed provider failures, and propagates coroutine cancellation. `ProviderWorkerDispatcher` is the worker-side SDK operation dispatcher: it validates request frames, initializes the factory with the host manifest and settings, routes declared provider capabilities to typed SDK contracts, and disposes partially initialized providers after failure. The process launcher must create its broker-backed `ProviderContext` and load the provider factory only after native isolation is established. `StreamExtractor.canExtract` is an asynchronous typed result so matching can be performed in the isolated process instead of executing provider code in the host process.

`ProviderWorkerSession` implements the common host-side request loop over a supplied frame transport. It validates response correlations, bounds concurrent host and broker requests, limits concurrent HTTP broker calls, applies broker deadlines and cancellation, and assembles request blobs only after ordered chunk, exact-length, checksum, and correlation checks. Concurrent incoming blobs reserve at most 64 MiB in aggregate. HTTP broker payloads are limited to 8 MiB; backup payloads retain the 32 MiB protocol limit. Broker HTTP response bodies are returned as bounded chunk transfers with host-generated transfer IDs rather than embedded in a JSON frame.

`ProviderWorkerRuntime` implements the worker-side asynchronous request loop over a supplied frame transport. It supports broker callbacks while provider initialization or invocation is suspended, cancellation of in-flight work, blob delivery, and persistence callbacks for synchronous SDK setting updates. `ProviderWorkerBrokerContext` supplies providers with a Ktor HTTP client backed exclusively by broker requests, the initial settings snapshot, brokered mirror lookup, and brokered stream resolution. The HTTP engine rejects request and response bodies above its configured bounds; the HTTP redirect plugin routes each follow-up request through the broker as a new operation.

`JvmProviderWorkerFrameTransport` provides bounded UTF-8 JSON-lines framing over supplied JVM streams and requires the caller to inject its blocking-I/O dispatcher. These SDK components still depend on a platform host broker and a trusted launcher to supply the frame streams only after native isolation. They do not themselves launch a process or establish native sandbox policy. No application platform may report sandbox availability based on these SDK primitives alone.

The IPC types do not themselves grant access. The host must check the provider's declared capabilities before every invocation, enforce `manifest.hosts` for the initial HTTP URL and every redirect, apply request/response and execution limits, and service all requests through the host broker. Providers must never receive host filesystem access or direct network access. A missing or failed native sandbox or broker remains a hard execution failure; this protocol is not a sandbox by itself.
